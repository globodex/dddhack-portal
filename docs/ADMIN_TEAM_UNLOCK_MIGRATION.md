# Admin team unlock migration

The append-only PostgreSQL migration `0106_admin_team_unlock.sql`, SQLite migration `0027_admin_team_unlock.sql` and Drizzle mirror `0029_admin_team_unlock.sql` replace only the existing lock-delete guard. They add no table, column or trigger, change no stored rows and leave every prior SQL file unchanged. PostgreSQL retains 69 logical portal tables and 282 triggers.

Deletion of a lock requires the exact valid write guard `admin-team-unlock:` followed by `JSON.stringify([teamId, lockedAt])`, using the persisted lock timestamp. Missing, stale, differently serialized and wrong-team tokens fail. A stored `valid=0` guard is already prohibited by its existing CHECK constraint. Frozen results block both unlock and terminal cascade. Any committed submission version or durable attempt greater than zero blocks admin unlock, including a retained attempt after content was terminally removed. The existing exact `cascade-team:` exception remains available for terminal deletion before results freeze; it cannot authorize an admin unlock under another token.

Removing the actual lock restores the existing pre-lock idea and membership behavior. It preserves team identity, crown, memberships, idea/revisions, project draft, submission payload/history, attempts, credits and audit rows. Existing application permissions, capacity, registration and deadline checks remain authoritative. No recruiting flag is introduced. The parent separately owns action authorization, timestamp/deadline compare-and-swap, audit of old lock metadata, and UI; this migration does not claim to test that separate integration.
