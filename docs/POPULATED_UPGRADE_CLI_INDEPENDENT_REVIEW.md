Initial review source: `d3c32d3`. Final implementation reviewed: `e1d50c27ef0785a93faf4c2e1f48929937d65aac` plus narrowing fix `59246860b49d83412c6685e4643f97a21aab55e5`. This review is local only. No hosted database, credential, provider setting, recovered benchmark fixture, hosted migration or deployment was accessed or changed.

## Required contract agreed before implementation

- Plan output is the default and makes no database connection. Database inspection and populated apply use explicit distinct options; unknown flags are rejected, and connected modes reject the synthetic flag.
- The operator privately supplies the intended host, database and role. Verify the connection URL without printing it, refuse target-changing URL parameters and pooled endpoints, and compare actual `current_database()` / `current_user` on the connection. A receipt contains a target digest rather than the private identity or URL.
- Apply requires an owner-acknowledged backup/restore checkpoint identifier and explicit confirmation that restore was verified. This supports a verified branch restore point; a local dump file is not mandatory. The tool must not claim it independently verified or created a backup.
- Pin the complete nine-entry source plan. Require every historical name/checksum pair, reject unknown or mismatched ledger entries, and reject `0103` without `0102`. The only permitted pending names are `0102_credit_stock.sql` and `0103_project_media_limits.sql`.
- Recheck the actual target, ledger and inspected table counts on the same connection under the migration's `SERIALIZABLE` transaction and advisory lock before any schema creation/apply. A missing ledger is a refusal, not permission to initialize a populated target.
- Receipt files are exclusive writes, expire after the agreed window and must match the locked preflight. Existing table counts and the new history/category associations are checked before commit. Failed postconditions roll the transaction back.
- Shared output contains stable status codes, migration names/checksums and counts only. Raw errors, SQL, connection URLs, credentials, row contents and checkpoint identifiers must not enter receipts or logs. No startup migration, seed/reset or production allocation is part of this command.

The earlier documentation-only sample checks its ledger before calling the migrator. Its exclusive operator window reduces a race, but an executable CLI should perform the decisive checks inside the same locked transaction. The proposed optional migrator hooks address that issue while preserving the existing checksum and ordering guards.

## Limits and evidence

PGlite is a local single-connection PostgreSQL engine, not evidence of hosted ledger contents, native multi-connection behavior or actual Windows execution. Counts are preservation checks; they cannot establish equality of every hosted row value. The independent fixture tests additionally compare persisted domain rows. An actual backup/restore checkpoint remains the owner's responsibility, with the documented exclusive migration window.

Evidence is in `evidence/populated-upgrade-cli-independent/`. Reusable tests are `tests/populated-upgrade-independent.test.ts` and its fixture helper. The recovered benchmark SQLite file was neither read nor modified. No push, merge, hosted migration, production allocation, provider change or deployment was performed by this review.
