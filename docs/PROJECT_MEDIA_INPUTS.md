# Project image input and storage contract

Original files and saved web images have separate limits. Both kinds accept PNG or JPEG, any aspect ratio, with source axes between 64 and 4096 pixels. Logos accept at most 1,000,000 bytes; banners at most 5,000,000 bytes (decimal MB). SVG, animated PNG, remote URLs and MIME spoofing are rejected. The dependency-free browser preflight runs before image decoding or any request. Browser decoding follows it; the production database boundary fully decodes every saved raster with Sharp and a 4096×4096 input-pixel ceiling.

The active editor normalizes every newly selected file through canvas, stripping EXIF/GPS metadata while preserving its displayed orientation. It optimizes locally without cropping, padding or stretching the underlying pixels. Existing saved drafts and immutable history are not re-encoded or backfilled. PNG keeps transparency and its MIME; JPEG keeps JPEG. Its largest starting edge is 512 pixels for logos and 1600 for banners. JPEG quality candidates are 86, 80 and 76; an over-budget candidate reduces its edge by 20%, with at most 24 bounded steps. Thin images may have a saved short edge below 64 pixels because the aspect ratio is preserved. Saved canonical axes are 1..4096. Old already-valid images remain readable.

| Boundary              |                Logo |              Banner |
| --------------------- | ------------------: | ------------------: |
| Original file         |         1,000,000 B |         5,000,000 B |
| Canonical web image   | 131,072 B (128 KiB) | 393,216 B (384 KiB) |
| Field character guard |             180,000 |             525,000 |

The largest binary pair is 524,288 bytes, about 699,100 base64/data-URI characters. Original 5 MB bytes never pass through a Next JSON save. The portal streams at most 1,000,000 request bytes before parsing. Only `save-project`, `submit-project` and legacy `submit` may use that envelope; all other actions retain 600,000 bytes. Draft JSON, storage hydration and field schemas have matching bounded guards. The Next proxy keeps its existing streaming/auth behavior. The synthetic local backend uses the same upper envelope.

The existing signed storage API also validates actual original-file bytes at the 1 MB/5 MB limits, fully decodes them, applies EXIF orientation, strips metadata and produces the same canonical budgets before writing an immutable object. Receipt actor/team/revision/leadership/check-in/lease/expiry/hash checks remain in place. Canonical JSON saves preserve their validated bytes exactly so existing idempotency hashes are unchanged. Public project DTOs retain versioned image URLs or validated reference metadata, never these full image strings.

## Manual database requirement

`neon/migrations/0103_project_media_limits.sql` is an additive source migration. It replaces only four upload-table CHECK constraints: source bytes become kind-specific 1 MB/5 MB, canonical bytes become 128/384 KiB, saved width/height become 1..4096. It preserves 0004's checksum and all foreign keys, receipt state and serializable-transaction guards. Existing pending, ready and consumed rows remain valid. The owner must review/apply the normal ordered PostgreSQL migration plan (including the separate 0102 credit migration) before relying on the widened existing signed API. No hosted migration was applied in this work. The active locally optimized JSON editor does not use signed browser PUTs and needs no CORS/provider-setting change.

## Verification

Focused tests cover exact decimal source boundaries and one byte over, real JPEG full decoding at both boundaries, signed API declarations before any intent/sign/write, arbitrary portrait/square/ultrawide aspect, thin canonical axes, PNG alpha, high-entropy noise, malformed/signature/MIME/truncated raster, dimension/decompression bounds, canonical request envelopes, private reference injection, tamper/hash checks, idempotency, lease/concurrency/authorization and public-list zero-object-read projection. The additive upgrade is exercised against existing pending/ready/consumed rows with real PostgreSQL semantics in disposable PGlite, including rollback on invalid mixed writes. PGlite does not establish multi-connection MVCC behavior.

Synthetic quality fixtures and equal-sized original/optimized previews are generated by `scripts/qa-project-media-quality.ts` into `evidence/project-media-quality`. They demonstrate actual output dimensions, bytes, transparency and typography. They are synthetic inputs, not claims about all photographs. Complex alpha/noise images reduce dimensions more to meet their web budget. Actual integrated Next HTML/RSC and API responses were measured at source `28ebbfc81a49ab839316b0d9121902e3cf645173`. All 22 expected-status/type/size receipts passed; the maximum uncompressed HTML was 2,284,333 bytes for three committed versions. See `evidence/project-media-response/README.md` for API, RSC, request bytes, hashes and rejected harness attempts. These are local payload measurements, not a hosted speed claim.
