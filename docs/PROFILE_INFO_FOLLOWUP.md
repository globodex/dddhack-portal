## Reversible roster removal: read-only findings, implementation held

The parent approved reversible removal for both never-signed-in roster emails and existing participants, preserving account/history and requiring explicit admin restoration. No removal implementation is included here. The remaining product decision is whether removal retains its occupied team seat and pauses active approval, or detaches the person, frees the seat and restores them teamless. The dedicated email-keyed migration is an engineering plan, not a separate requested schema-approval gate.

Existing `participant-deactivate` stores a recoverable user-ID `record_removals` entry. It preserves memberships, occupied slots, team/idea/submission/credit records and approval state, and blocks removal of an active team leader until a successor is explicitly transferred. Owner/staff/self are protected. Existing restore clears the user-ID tombstone. Sessions/login do not remove it; roster import skips known removed accounts. Never-signed-in emails lack a user ID, so existing controls cannot remove them.

`record_removals.target_id` has no target-user foreign key, but its kind enum excludes a new email kind. Legacy trusted Sites identities accept arbitrary ID strings, so a `roster-email:<email>` target cannot be proven collision-free without changing auth identity policy. Do not overload user-ID targets or reserve an external identity prefix.

Minimal next-step recommendation: as the engineering plan, add a dedicated `roster_access_removals` table in a future additive migration using a then-unused number (the earlier0107 proposal was never implemented;0107 is now assigned to `0107_admin_team_lock.sql`), keyed only by centrally normalized email, with active flag, actor, timestamp and reason. It represents participation revocation, not account deletion or an identity. Preserve existing user-ID removal records and enforce active user-ID OR email revocation consistently in actor/session-derived participation, roster checks, imports, discovery/contact/credit reads, admin counts and write guards. Login/session refresh and CSV reimport must never clear either record. Only existing authorized admin restore clears both for the reviewed account/email. No arbitrary client-supplied kind or identity prefix is accepted. Owner/staff/self protections and the explicit successor requirement for leaders remain. That separate roster recommendation is not implemented and has not modified schema or ledger files. The user subsequently chose detach/free-seat for nonleaders and teamless on explicit restore. Implementation remains separate and excluded from this release; leader removal still requires an explicit successor rather than deletion or automatic appointment.

A separate derived-state concern was reported before editing: `teamFacts` currently counts retained memberships and approved registrations without a participant-removal predicate. A removed Going member can therefore leave `allApproved=true`, while attendance is revoked. Preserving occupied slots/history but excluding inactive members from computed active readiness is a proposed correction, pending parent coordination; this follow-up does not silently rewrite approvals or change that derivation. An admin member display may also need an explicit Removed label instead of implying that the retained prior status means active participation.

No permanent deletion, cascade, credit retirement, role change, team deletion, leader auto-selection or automatic re-enrollment is proposed by the reversible-removal request.
